# Планы развития и отложенные решения

Здесь хранятся направления развития и заметки обсуждений. Это не описание
текущей архитектуры и не список обещанных функций: актуальная структура —
в README. Изменения поведения и схемы БД выполнять отдельными задачами.

## Масштаб и подход

Один VPS: 1 CPU, 2 ГБ RAM, PostgreSQL, бот и несколько лёгких приложений.
В чате около 50 участников и 200 сообщений в сутки.
Сохраняем один процесс бота и PostgreSQL, добавляем функции постепенно.
Микросервисы, брокер очередей, Redis, векторная БД и агентный фреймворк
сейчас не нужны.

## Принятые направления

- Неделя — скользящие семь суток, а не календарная неделя. При сборке отчёта
  фиксировать один момент окончания и использовать интервал
  `[окончание − 7 суток, окончание)` для всех его частей.
- Для недельного дайджеста хранить сообщения чата семь суток. Это отдельные
  временные данные: историю зарегистрированных подходов по этому правилу
  не удалять. Сбор сообщений и очистка пока не реализованы. - feature plan
- Комментарий к подходам и дайджест переписки — отдельные задачи с отдельными
  промптами, использующие общий LLM-клиент и обработку ошибок.

Срок хранения не определяет размер контекста LLM. При текущей активности
неделя — около 1400 сообщений, но объём зависит от их длины. Перед реализацией
оценить токены реальной недели и доступный контекст выбранной модели с запасом
для инструкций и ответа. Если целиком не помещается, обрабатывать частями
и собирать итог из промежуточных выжимок. Молча отбрасывать конец недели нельзя.

Сбор отчёта и очистку нужно согласовать: сначала зафиксировать входные данные
периода, затем удалять устаревшие строки. При задержке запуска за пределы срока
хранения часть данных уже может отсутствовать; такой отчёт должен обозначать
неполноту. Хранение ровно семь суток не даёт запаса для восстановления отчётов
за прошлые периоды. Политику резервных копий временных сообщений определить
при реализации.

## Пока не меняем

- Маршрутизацию: помнить, что общий обработчик `HasText()` может перехватывать
  сообщения до новых обработчиков. Вернуться к фильтрам при добавлении функций.
- Ограничения БД, защиту от дублей и обработку частичных сбоев: оставить
  отдельной будущей задачей. Перед изменением существующей схемы нужны
  миграция и проверка текущих данных.
- Синхронный psycopg2: для текущей небольшой нагрузки допустимо оставить.
  Медленный SQL или блокировка БД задержат остальные события бота.
  Вернуться к этому при заметных задержках либо появлении тяжёлых запросов.
  Само объявление `async def` блокировку не устраняет.

Изоляцию статистики по `chat_id` учитывать перед использованием в нескольких
чатах; сейчас запросы общего отчёта объединяют данные всех чатов.

## Другие функции: ориентир на будущее

Это сохранённые рекомендации для обсуждения, не согласованный список работ.

- Графики: БД считает суммы по дням или месяцам, бот строит картинку.
  Построение не должно надолго останавливать ответы на сообщения;
  начать с одной генерации одновременно.
- Выбор периода: добавить его к существующему меню спортсменов. Сейчас
  период отчёта фиксирован. Для простого выбора постоянное состояние
  диалога не обязательно.
- Расписание: помнить в БД, какой отчёт уже подготовлен и отправлен,
  чтобы перезапуск процесса не сбрасывал эту информацию.
  Решение о пропущенных запусках принять вместе со сроком хранения сообщений.
- Важные напоминания: если появятся, отдельно продумать повторную отправку
  после сбоя и возможные дубли; сейчас очередь доставки не строить.
- Эксплуатация: определить резервное копирование, восстановление и ротацию
  логов. Действующий systemd-сервис и команды перезапуска зафиксированы
  в `development.md`.
