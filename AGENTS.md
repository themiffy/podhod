# Подход Бот: инструкции для работы в репозитории

## Назначение и устройство

Небольшой Telegram-бот на aiogram 3. Считает объёмы пива из сообщений
`#подход #имя 0,5л комментарий`, хранит их в PostgreSQL и формирует `/stats`.
Сохранять простоту: не добавлять фреймворки и слои без конкретной необходимости.

- `main.py`: запуск polling, настройка команд, времени жизни пула БД и HTTP-сессии LLM.
- `routers/podhod_router.py`: регистрация/редактирование подходов и ответов.
- `routers/commands.py`: `/help`, `/stats`, `/stats имя`, сбор числового отчёта.
- `app/utils.py`, `app/filters.py`: разбор сообщений, фильтры, отправка текста.
- `app/database_func.py`, `app/connection_pool.py`: SQL и пул psycopg2.
- `app/llm.py`: единый сервис комментариев к статистике.
- `app/llm_prompts.py`: персонаж и постановка задачи модели.
- `app/llm_client.py`: асинхронный API-клиент и контракт `ChatClient`.
- `app/llm_config.py`: настройки LLM; окружение приоритетнее `env.json`.
- `db/schema.sql`: исходная схема PostgreSQL 15.8 из дампа; только для новых БД.
- `tests/support.py`: запись Telegram API-запросов без внешней сети.
- `tests/integration/`: сценарии с настоящей PostgreSQL и подменой Telegram/LLM на границах API.

## Правила изменений

- Сначала смотреть `git status` и diff: сохранять изменения пользователя.
- Поддерживать Python 3.9+ (текущий `venv` — Python 3.9).
- Сохранять стиль персонажа и язык ответов. Не менять его молча при замене API.
- Оба вида статистики используют один `StatsLLM.generate`; не дублировать запросы.
- Не выполнять синхронные сетевые LLM-вызовы в обработчиках aiogram.
- Промпты не должны зависеть от поставщика. Специфические поля API — в адаптере.
- Для совместимого Chat Completions API менять конфигурацию. Для другого
  протокола реализовать `ChatClient.complete` и подключить клиент в `main.py`.
- Числовой отчёт считать по БД; ошибка LLM не должна мешать его отправке.
- История подходов — пользовательские данные, передавать её в user-сообщении.
- Не логировать ключи, историю, ответы модели и тела ошибок API.
- Не читать/печатать секреты из `env.json` без необходимости; не коммитить файл.
- Не запускать polling и не делать платные API-вызовы для обычной проверки.
- Не менять схему/данные рабочей БД для тестов. `db/schema.sql` не применять
  к существующей БД; отдельного механизма миграций пока нет.
- Пулы, боты, чтение конфигурации — только при запуске, не при импорте модулей.
- Для каждого диспетчера создавать новые роутеры через `create_router()`.

## Проверка

Установленные зависимости находятся в `venv`; список — `reqs.txt`.

```sh
venv/bin/python scripts/check.py
```

Обычный прогон не должен требовать PostgreSQL, Telegram, LLM-ключей или выхода
в сеть. При изменениях SQL, пула БД, роутеров или регистрации подходов запускать
также `venv/bin/python scripts/check.py --integration`. Команда использует локально
установленную PostgreSQL, создаёт временный кластер без TCP, после прогона
останавливает его и удаляет данные, в том числе при ошибках тестов. Docker не
использовать, конкретную версию PostgreSQL для тестов не устанавливать.
При необходимости указать каталог бинарников через `PG_BIN`. Не использовать
`env.json` или рабочую БД для тестов. Каждый сценарий работает в отдельной UUID-схеме.

Рабочий сервер: VPS, PostgreSQL 15.8 на том же VPS. Сейчас выкладка — `git pull`
и ручной перезапуск процесса. GitHub Actions отложены. Не предполагать имя systemd
сервиса или способ перезапуска: они пока не зафиксированы пользователем.
Цикл разработки и команды тестового стенда — в `docs/development.md`.
